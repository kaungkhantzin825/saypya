### Build gotcha

`npm run build` fails in this environment when `public/build` already has >50 files: Vite's
`emptyOutDir` calls `fs.rmSync`, which trips the sandbox bulk-delete guard. Vite skips
`emptyDir` entirely when the outDir does not exist, so the reliable fix is to delete
`public/build` (in batches of ≤50) before building. This is a **local sandbox artifact
only** — on the Linux server `npm run build` works normally.

## Applied the SanPya logo, and fixed four real bugs found while testing

Goal was: use `public/images/SanPya-Logo.png` as the brand mark, test it, and report the
test accounts. Testing exposed a broken app, so this turned into a debugging session.

### The app would not boot at all (git merge in progress)

`routes/web.php` contained unresolved conflict markers (`<<<<<<< HEAD` at line 105), so
`artisan serve` died with a ParseError and every request 500'd. A merge was in progress
(`.git/MERGE_HEAD` = `df748b2 "fix error"`) against local commit `281a41f "status fix"`.
Conflicts: `routes/web.php` and `package-lock.json`.

The `routes/web.php` conflict was a genuine both-sides-broken situation:

- **HEAD** — an inline closure rendering `Inertia::render('Pages/Contact', ['captcha' => …])`.
  It rendered the Vue page but never wrote `session('contact_captcha')`, so
  `ContactController::submit()` (which validates against that session key) always failed.
- **Incoming** — `Route::get('/contact', [ContactController::class, 'show'])`, whose
  `show()` returned `view('pages.contact')` — **a Blade file deleted in this session**.

Resolution: keep the incoming controller route and rewrite `show()` to render the Inertia
page *and* set the session captcha, satisfying both sides. `package-lock.json` is still
unresolved and left for the user.

### MySQL was not running

Requests then failed with `SQLSTATE[HY000] [2002] … actively refused`. XAMPP's MariaDB was
simply down. `sc.exe` is on the sandbox program blacklist, so services cannot be queried;
start the daemon directly instead:

```bash
/c/xampp/mysql/bin/mysqld.exe --defaults-file="C:/xampp/mysql/bin/my.ini" --standalone
```

Pre-existing noise in `mysql_error.log` (an unopenable `password2.wp_users` tablespace and
an InnoDB LSN warning) is unrelated and harmless for this app.

### Lecturer and admin could not log in

`AuthenticatedSessionController::store()` redirected to `route('dashboard')`, and
`StudentController::dashboard()` bounces non-students on to their own panel. For students
that is a single redirect (fine), but for lecturers/admins it is a *second* redirect that
the Inertia client does not follow — the browser stayed on `/login` showing the form.
Verified over HTTP that the server-side chain was correct (302 → 302 → 200), so it was
purely a client-side Inertia limitation. Fixed with `Inertia::location($panel)` for
non-students, which issues a 409 + `X-Inertia-Location` and forces a full page load into
the still-Blade panel. `store()` now returns `Symfony\…\Response`.

### Every uploaded image pointed at port 8000

Course thumbnails and hero slides 404'd. Four models built storage URLs by hand from
`config('app.url')` instead of using `asset()`, pinning them to `APP_URL`
(`http://localhost:8000`) regardless of the port actually being served:
`Course::getThumbnailUrlAttribute`, `HeroSlide::getImageUrlAttribute`,
`SiteSetting`, `User::getAvatarUrlAttribute`. All four now use `asset()`, which is
request-relative, so images work on any host/port with no `.env` change.

### Instructor avatars were empty

`avatar_url` is an accessor on `User` but `User` had **no `$appends`**, so it never reached
the Vue layer — every `<Avatar>`/`<img :src="…avatar_url">` (~10 call sites) rendered empty.
This is exactly the pitfall already documented for Course/Lesson/HeroSlide/BlogPost; `User`
had simply been missed. Added `protected $appends = ['avatar_url'];`.

### Bugs found and fixed while verifying

- **Type errors in every `DataTable` call site (20 of them).** The component's generic was
  `T extends Record<string, unknown>`, which demands an index signature that real interfaces
  (`User`, `Enrollment`) do not have. Relaxed to `T extends object` and routed dynamic column
  access through a single `valueOf()` cast.
- **`Enrollment` type was missing the `user` relation** (it declared `course` but not `user`).
- **Mobile horizontal overflow — page was 740px wide on a 390px viewport.** The table's
  `min-w-[42rem]` propagated up through the `Card`, because grid items default to
  `min-width: auto`. Fixed with `min-w-0` on the grid, the card and the table wrapper.
  `diag-overflow.cjs` now reports this class of bug directly.
- **Server-side sorting was not wired.** `DataTable` emitted `update:sort` but the page
  ignored it. Implemented properly: `usersIndex` accepts `sort` + `direction` (whitelisted
  against an explicit column list before being interpolated into `orderBy()`), and the page
  forwards them as query params. Columns are now marked `sortable`.
- **Toggle-status flash read "User account inactived successfully!"** — string concatenation
  produced "inactived"/"actived". Now "activated"/"deactivated".
- **Dashboard "Top courses" showed `N/A` for every instructor** — the `instructor` relation
  was never eager-loaded. Also added `enrollments` to the eager load, because
  `Course::getTotalStudentsAttribute` falls back to a COUNT query per row (N+1).

### Key discovery: `data-page` is stale after SPA navigation

Chasing a test failure where the URL said `/admin/users` but the component still read
`Admin/Dashboard`, I found that **`@inertiajs/core` only *reads* `el.dataset.page` at boot
and never writes it back** (verified in `node_modules/@inertiajs/core/dist/index.esm.js` —
the only `data-page` reads are in the boot path). So the attribute is a snapshot of the
*first* page of the session. This invalidates the `grep '&quot;component&quot;…'` trick
that was documented as a general verification method; it is only valid on a cold load.
Corrected in both `FRONTEND_GUIDE.md` and `MEMORY.md`.

Related: Inertia pushes the new URL to history *before* it swaps the component, so polling
`window.location.pathname` can observe the new URL while the old component is still mounted.
Tests must gate on rendered DOM, not the URL.
